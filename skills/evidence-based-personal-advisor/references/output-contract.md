# Compact career output contract

Use the shortest structure that preserves decision quality.

## Decision-first layer

Make the first screen useful to a tired or inexperienced user:

1. **Bottom line** — one decision or direction in 3–5 plain-language sentences.
2. **Next three actions** — no more than three, ordered. For each show `action`, `why now`, `effort`, and `done when`.
3. **Main uncertainty** — the one limitation most likely to change the recommendation.

Put evidence detail after this layer. Avoid unexplained acronyms, evidence-method names, and framework terminology here. Give the user a smallest viable first step that can normally begin in 15–30 minutes.

## Standard answer

After the decision-first layer, include only the sections needed:

1. **What the evidence says** — 3–7 findings with dates, geography, confidence labels, and nearby citations.
2. **What this means for you** — connect findings explicitly to the user's evidence, constraints, and goals.
3. **Evidence or competency gaps** — compact table only when comparison is useful.
4. **Later actions** — at most two beyond the first three; mark them as optional or later.
5. **Uncertainty and limits** — coverage gaps, conflicting evidence, inaccessible sources, and assumptions.
6. **Review loop** — 2–4 metrics and a specific review date or trigger.

For job-search analysis, add a compact competency/evidence-gap table and a source-sample summary. The table should show hiring category, demand band, match status, candidate evidence grade, gap type, and action priority when those distinctions affect the decision. Report usable JD counts by source and material platform-access shortfalls. Offer detailed ad-by-ad extraction only when it would help; do not dump it by default.

If the user explicitly asks for a 30/60/90-day plan, cap each phase at three outcomes and state the approximate weekly effort. Put only the first seven days in the immediate-action layer. If the requested plan exceeds the user's stated capacity, reduce scope and identify what was deferred.

## User comprehension check

Prefer observable comprehension over asking whether the answer was “good.” During a beta test or follow-up, ask at most these three short checks:

- What is the first action you will take?
- Which recommendation feels unrealistic or unclear?
- How much time can you actually spend this week?

Do not add these questions to every answer. Never treat a positive rating as evidence that factual claims were correct.

## Epistemic labels

Use these inline when ambiguity matters:

- `Fact:` directly supported observation.
- `Inference:` reasoned interpretation from cited facts.
- `Forecast:` future claim with assumptions.
- `Recommendation:` personalized action based on evidence and user values.

Do not label every sentence. Apply labels at boundaries where readers might confuse evidence with judgment.

## Token discipline

- Lead with the answer; omit research diary unless requested.
- Cite the strongest source for a claim rather than every redundant source.
- Summarize repeated job requirements into normalized categories.
- Put supporting detail in tables only when comparison benefits.
- Avoid generic advice, model histories, long quotations, and repeated caveats.
- Do not expose internal model-selection or evidence-grading detail unless it changes the decision or the user asks.
- If more useful detail exists, state the next optional drill-down rather than including it automatically.
